Document version: 1.0Product: The Digital MuseumSecurity posture: Small public portfolio with a private owner/admin areaRecommended architecture: Next.js + Supabase Auth + PostgreSQL + Supabase Storage + RLS
The most important security decision is also the simplest one:
Almost everyone is a visitor. Only you are an administrator.
That means we should not build a complicated permission system for V1. We should make public content genuinely public, keep management capabilities private, enforce authorization in the database, and use MFA for the admin account.
Supabase Auth fits this architecture because it integrates authentication with PostgreSQL Row Level Security, allowing database access to be controlled according to the authenticated user's identity. 

1. Security Goals
The Digital Museum has five primary security goals.
1. Protect the admin account
An attacker must not be able to log into the private management area or take control of the museum.
2. Keep unpublished content private
Draft projects, unpublished experiments, private media, and internal settings must never accidentally appear publicly.
3. Prevent unauthorized database changes
A visitor should never be able to:
edit a project, 
publish content, 
delete media, 
change your profile, 
change site settings. 
4. Protect secrets
Database secret keys, SMTP credentials, API keys, and other credentials must remain server-side.
5. Fail safely
When something breaks, the user should get a useful message without seeing stack traces, database errors, secrets, internal paths, or other sensitive implementation details. OWASP specifically recommends generic authentication errors and avoiding sensitive information in error responses.

3. Authentication Strategy
Recommended: Supabase Auth + Email/Password + MFA
For the owner/admin account, I'd use:
Email + password + MFA
Supabase supports password authentication, magic links, OTP, social login and other methods. 
For this product, email/password + MFA is the most straightforward choice.
Why?
Because this isn't a consumer SaaS product with thousands of users.
You only need to protect a tiny number of privileged accounts.

enter the museum,

There is no reason to create an account system for portfolio visitors.
That dramatically reduces your attack surface.

11. Row-Level Security Strategy
This is one of the most important parts of the system.
Every exposed database table must have an explicit access policy. Supabase recommends enabling RLS on every table in an exposed schema and separately controlling table grants and policies. 
Our central rule:
Deny by default; explicitly allow what the role needs.

26. Admin Authorization
Do not determine admin status from something like:
if (email === "myemail@gmail.com")
That is brittle and dangerous.
Instead, use an explicit role/claim or a tightly controlled server-side admin mapping.
For a single-owner V1, a simple profile.role = 'admin' combined with server-side verification can work.
The key is:
The browser must never be able to grant itself admin status.

28. Session Security
Use the framework's server-side auth integration.
The application must:
use secure cookies 
avoid putting access tokens in localStorage unnecessarily 
refresh sessions safely 
invalidate sessions on sign-out 
protect admin routes server-side 
For Next.js + Supabase, use the SSR-oriented Supabase integration rather than inventing your own session system.

29. Password Rules
For the admin account:
use a long, unique password 
do not reuse it elsewhere 
use a password manager 
enable MFA 
don't store the password anywhere in the codebase 
don't share credentials via GitHub/Discord/WhatsApp 
The most likely admin-account compromise is usually not some exotic database exploit.
It's:
password reuse + phishing + leaked credentials.

30. Environment Secrets

Only public configuration should be browser-visible.
Supabase specifically distinguishes publishable keys from secret keys and recommends keeping elevated secret keys in trusted server-side components.

67. The Security Principle for V1
If I had to reduce this entire document to six rules, they would be:
1. Visitors don't need accounts.
Less authentication = less attack surface.
2. You are the only administrator.
Don't build roles you don't need.
3. MFA protects the admin.
Your admin account controls your entire portfolio.
4. RLS is the final authority.
Never trust the frontend to protect data.
5. Unpublished means invisible.
Draft content must be impossible for anonymous users to read.
6. Errors fail safely.
Users get useful messages; attackers don't get your internals.
The combination of least privilege, deny-by-default authorization, server-side checks and database-level RLS follows established application-security guidance from OWASP and Supabase.
